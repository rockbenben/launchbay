## 四、发现 1 —— 镜像构建在 Linux 上把一条门禁打红（这是缺陷，不是环境问题）

> **这一节的结论已被第八节取代**：缺陷已按候选 1 修掉并复验。留着原文是为了记下「Windows 门禁绿、Linux 门禁红」这一类病是怎么被抓到的，别把它当今天的发版判定读。

```
#11 8.112 --- FAIL: TestPrefs_主题改得动且立刻看得见 (0.01s)
#11 8.112     prefs_test.go:44: 改了主题而页面没变：缓存键里少了 profile.json 的指纹
```
同一份代码在 Windows 上跑同一测试是绿的。在同一个 Linux 容器里实测连续两次原子替换的 mtime：

```
第一次 mtime=2026-10-07T06:00:19.611087525Z
第二次 mtime=2026-10-07T06:00:19.611087525Z     相等=true
```

**根因**：渲染缓存键的 `profileMtime` 那一维**依赖文件系统时间戳粒度**，而粒度并不保证比"写完立刻读"更快。
Linux 的 tmpfs/overlayfs 在同一时钟刻内两次写会给出**完全相同**的 mtime；真实部署更糟——
`data/` 走 CIFS/9p 挂载（群晖、Docker Desktop 的 bind mount）时时间戳常常只到秒。
后果不是测试红，是**家属按了主题按钮而页面不动**，直到下一次别的写入把 mtime 推过去。

书签那一维没这个毛病：`rev` 是内容派生的，写一次必然变；`mtime` 只是"外部改盘"的补充信号。
`profile.json` 没有 rev，所以它这一维现在没有任何不依赖时间戳的兜底。

**三个候选处置**（未动代码，等裁定）：
1. 缓存键把 `profileMtime` 换成 profile.json 的内容指纹（一次 ~250 B 的读 + 哈希，命中路径多一次小读，
   彻底不依赖时间戳粒度）——判据仍只有一份，代价是每次请求多一次小文件读。
2. `/prefs`（与改 PIN 的写通路）写完直接让该档案的缓存条目失效——快，但把"键自洽"变成"写的人记得清"。
3. 保留现状 + 文档写明"主题改动最坏延迟到下一个时间戳刻度"——不推荐，这是用户可感知的失灵。

这条也说明 Task 8 那条 CI 值得存在：**CI 跑在 ubuntu-latest 上会抓到它**，我本机的 Windows 门禁抓不到。

## 五、测量方法账（三条假红都是工具的错，写下来免得下轮重犯）

跑这 37 条的探针脚本在 `probe.py`（同目录），运行前提与「唯一碰磁盘的那一段」都写在文件头。上一版它只活在 `.superpowers/tmp/` 里——那份是 gitignore 的草稿，验收文档说自己可复现而脚本不在仓库，就是假话（整枝评审 I-5）。

   而浏览器接受（本轮用 `fetch('/switch')` 走真浏览器，status=200 且切档生效）。
   我为了断状态码而关掉自动跟随重定向，于是 cookie 被探针自己丢掉，"管理员切档后没横幅"是假红。

## 八、发现 1 的处置（同日跟进，选了候选 1）

缓存键里 `profile.json` 那一维从 mtime 换成**内容指纹**（`Store.LoadProfileWithFingerprint`
= 同一次读盘给出解码结果与那份字节的 sha256），`Store.ProfileMtime` 随之删除（没有别的读者）。
同一天的整枝评审补了后半：键里的 `home` 也只放 id 是不够的（横幅印的是 home 的显示名），home 那份 profile.json 的指纹同样进键，见 `b28ef61`。判据仍只有一份：
读这份文件的是 `decodeProfile`/`Validate`，指纹只回答"变没变"。

新增一条确定性证人 `TestProfilePage_mtime没变而内容变了要重算`：把 mtime 按回改动前那个值、
只改内容，要求页面与 ETag 都反映新主题。它在改动前**先红过**（原文：
`render_test.go:265 内容变了而 mtime 没变，页面还是旧的` 与 `两次的 ETag 相同（"dad-2d056decd9ddbd18"）`），
并且在 Windows 上就能红——不再依赖某台机器恰好有粗粒度时钟。

配对的反向证人：把指纹改回"按 mtime 取哈希"，只有新那条红、
`TestProfilePage_改profile会重算` 照绿——这正好说明旧证人看不见这类病，
也是当初它在 Linux 上红、在 Windows 上绿的同一个理由。

两份 spec（§7.1 与 §13）与计划的"修订"段都按新形状改了字；发版判定里"卡在发现 1"
这一条随本次修复解除。当时还剩下的「镜像需按当前 HEAD 重建并跑一次 Linux 门禁」也已经在第九节做完并记了读数。
