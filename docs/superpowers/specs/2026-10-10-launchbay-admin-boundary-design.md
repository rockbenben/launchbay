状态：**P0 与停用档案已落地**（§3/§5，端点与 `lb_home` 处置全部实施完）；
**§6 共享清单已改判为不做**——见那一节开头的改判记录。本文件是**改判**——它推翻
§8.9「管理员可代管他人书签」与 §6.1 的跨档案写豁免。人是决定者（2026-10-10 本人拍板：
「完全不可见也不可改」、「`*` 只管账号」、「P0 + 共享 + 停用全做」；同日再拍板

> **2026-10-23 补抬头：这条边界后来又紧了一格，并多了一条免凭证的建档通路。**
>
> - **删档要那把机器级 key 本身**（新凭证档 `credAdminKey`）：`DELETE /api/v1/profiles`
>   只认 `Authorization: Bearer <LAUNCHBAY_ADMIN_TOKEN>`，只带 `lb_admin` cookie 一律 403；
>   页面那一步（`POST /admin/delete`）要在确认页上**再输一次**那把 key（缺了或不对就
>   一步都不删）。理由与本文同一个方向：**登着管理页 ≠ 有权删档**——删档是这台机器上
>   唯一不可逆的动作（快照跟着档案一起没了，`revert` 救不了它），而 `lb_admin` 是那把
>   key 的**派生值**（进 devtools、进导出、进浏览器同步）。
> - **非管理员自己建一份**：`POST /api/v1/profiles/new` 与 `POST /new` 免凭证，id 由名字
>   派生（不接受申报）、建完**不发会话**。它**不授予任何读取别人书签的权限**（建出来的
>   是空的、只属于它自己的 PIN），所以**不破坏本文那条边界**；代价明写：局域网里任何设备
>   都能建档，选单页上会多出一张卡（管理员随时能删掉它）。
>
> 形状与判据见权威源 `2026-10-05-launchbay-design.md` §6.1/§8.8/§11 与 AGENTS.md。

## 0. 触发：市场上没人这么做

| 产品 | 管理员对他人内容 |
|---|---|
| **Nextcloud** | 管理员账号「可以配置和维护实例，但**默认无权访问第二个用户的文件**」。能做的敏感动作是**重置对方密码**。要代人操作必须显式装 `impersonate`（opt-in，默认关）。社区共识原话：*Private data is none of the admin's business.* |
| **Linkding** | 「每个用户有**各自独立**的书签库」「**默认不共享**」。管理员在 Django 后台做的是 Users → Add user，**不是打开别人的书签**。共享是逐条书签 opt-in 的 `shared` 标志。 |
| **Homarr / Dashy / Heimdall** | 多用户与角色都有，但那些权限管的是**谁能看到哪块面板**，不是「管理员进去替你整理」。 |

**共识一句话**：管理员管**账号**，不管**内容**。内容默认私有，共享要显式 opt-in。

## 1. 问题（现状的实测事实，不是推测）

1. `internal/httpapi/routes.go` 的 `require()` 第 162 行：
   `if profileID != "" && profileID != sess.Active && !s.activeIsAdmin(sess) {` —— 管理员会话
   对**任意档案**的读写一律放行。
2. `internal/auth/token.go` 的 `Scope.Allows()`：`s.Profile == ScopeAny || s.Profile == profileID`
   —— `*` 令牌对**任意档案**的内容端点一律放行。
3. `internal/httpapi/switch.go` 的 `to=<id>` 分支：管理员免 PIN 直达别人的台，
   之后写通路就落在那个人身上，顶栏挂「正在管理 X 的书签 · 由 Y 操作」的横幅（§8.9 专门设计的）。
4. `/admin` 的「进入编辑」按钮就是 `POST /switch to=<id>`。

于是现状是：**管理员不但能改，还能看**（`GET /api/v1/data?profile=<别人>` 与 `GET /api/v1/export` 都通）。

## 3. P0：边界收紧

### 3.1 两处判据

**会话**（`routes.go`）：跨档案一律拒，不再有管理员豁免。

```go
if profileID != "" && profileID != sess.Active {
    return "", auth.Scope{}, false
}
```

**令牌**（`routes.go` 令牌分支）：`*` 只过 `credAdmin` 端点。`credScoped` 一律拒——
不管 `profileID` 是不是空（credScoped 的空申报在函数开头已经拒了）。

```go
if sc.IsAdmin() && want != credAdmin {
    return "", sc, false
}
```

落点只有 `require()` 一处：端点层不各自再写一遍判据。

### 3.2 撤掉的三件东西

| 东西 | 处置 | 理由 |
|---|---|---|
| `/switch` 的 `to=<id>` 分支 | **整条删**（连同 switch.go:58-76 那段形状闸） | 它唯一的用途就是代管。`to=home`（退出管理）与 `to=picker` 一并删——没有管理态就没有"退出管理"，`home` 退化成"回自己的台"，与 picker 二选一即可，**留一个就够** |
| 管理横幅（`profile.tmpl` 的 `{{with .Manage}}`） | **删** | 它是"正在代管"这句提醒的载体，代管没有了它就是一句谎话 |
| `/admin` 的「进入编辑」 | **删**（`admin.tmpl` 的 `/switch` 表单 + `CanEnter` 那条形状闸） | 它就是 `/switch to=<id>` 的一枚按钮 |

`/admin` 剩下的动作：**设 PIN**、**删档**、**停用/启用**、**进入编辑（仅自己那一份？否——见下）**。

> 「进入编辑」在管理页里指的是"切进别人/自己那一台"。切进**自己**那一台没有任何意义（已经在里面），
> 所以这一格整体清空，改成「设 PIN / 停用 / 删档」三个账号层面动作。

### 3.3 `sessionLegal` 与 `Home` 的去留

`Session.Home` 与 `sessionLegal()` 是"代管态"的残骸：`Home != Active` 意味着正在管别人。
代管没了，于是 **`lb_home` 这条 cookie 整个作废**，`sessionLegal()` 退化成"形状合法"。

处置：`lb_home` 不再读写（保留字段以免磁盘上的旧 cookie 变成非法形状时崩），`sessionLegal()`
只判两条 cookie 是不是合法 slug。这是一次**降级而不是删除**——旧 cookie 仍被接受但不再有特权，
于是升级后不需要每个人清 cookie。

## 4. 审计线为什么不是后门

`/api/v1/history` 聚合对管理员开放，它会露出 `groups/nas/items/dsm` 这种路径。三点理由：

1. 它不含 value：`Item` 路径只有 id，`Name`/`URL`/`Desc` 一个都不在。
2. 拆掉它会让**每一份数据变更都无法追责**——而 §11 明确要"不误改"可退。
3. 它的判据是 `credAdmin`，与内容端点不是同一扇门。

真要再紧一档是"审计线也只给本人"，但那会让"家里人误改了、查不出是谁改的"变成常态。
**这一条记进 §15 开放项**，等人用一段时间觉得不够再说。

## 5. 停用档案（P1）

删档不可逆（`revert` 救不了它：快照跟着档案一起没了）。某人暂时不用了——孩子放假、
某人住院、租客走了——现在只能删。

**形状**：`profile.json` 加一个 `disabled` 布尔。

| 面 | 停用后 |
|---|---|
| `POST /pin` 用它的 PIN | **拒**（与 PIN 不对同一句话，不说"已停用"——那是枚举面） |
| `CountProfiles()` | **照数**——判据是目录数，停用的档案仍占位，引导窗口不会重开 |
| `ListProfiles()` / 选择页 | 照常列出（否则就是另一种枚举），但 PIN 一律拒 |
| 管理页 | 照常一行，标「已停用」徽标，动作换成「启用」 |
| `/admin/pin`、`/admin/delete` | 照常可用（管理员给停用的人改 PIN、重建，是正当操作） |
| 它的书签数据 | 一个字节不动 |

**动作**：`POST /admin/disable`（两步页面，与删档同一套两步确认零 JS 形状）。
启用复用同一条，判据取反。

**为什么不用目录旁边的标记文件**：`profile.json` 已经要读（选择页要拿 title），
多一个文件就多一份"两个来源说两件事"的可能。

## 6. 共享清单（P1）—— **2026-10-10 改判：不做**

> **改判记录（2026-10-10 当天，本人在复核时再次拍板）**：这一节整条作废，**不做**。
> 原拍板是「P0 + 共享 + 停用全做」，复核时改成了：**先把上手路径与文档清干净，
> 共享清单不做**。
>
> 理由不是"难做"（下面的形状一天就能写完），是**它与本案的定位相反**：
> §11 与 AGENTS.md 反复承诺的是"家里人各存各的、看不见别人的那一份"，而
> `/shared` 是全案唯一一处**默认让人读到别人的标题与 URL** 的通路。为了让
> "共享"这件事好用，它必然要跨档案汇总——而 §3 那一轮收紧的全部力气都花在
> 拆掉跨档案可见性上。为了一个非必需的功能把那条边界重新打开，是拿定位换功能。
>
> Linkding 的两层开关（每档案 `enable_sharing` + 每条 `shared`）没有改变这个判断：
> 那是给"公司/团队知识库"场景的，本案是家里三五个人的书签台，没有"对外发布"
> 这个需求。**决定写在这里是为了防止它被复活**——下一个人翻到这里看到一份写得很
> 完整的形状，很可能以为那只是还没做。AGENTS.md 的「禁止事项」里也钉了一行。

## 8. 明确不做（以及为什么）

| 不做 | 理由 |
|---|---|
| impersonate（像 Nextcloud 那样让管理员显式"变成"某个人） | 本案没有"合法理由"这个概念，也不该有。管理员改别人书签的唯一动机是帮人整理，而那是让本人自己整理更省事 |
| 审计线也收紧到只给本人 | 见 §4；记进 §15 开放项 |
| 公开的共享页 | 见 §6 |
| 组级共享（Linkding 的 bundle） | 先做条目级。真需要"全家收藏夹"是一个分组级开关，而不是每条都勾 |
