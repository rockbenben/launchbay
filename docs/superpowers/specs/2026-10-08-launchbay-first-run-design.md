# launchbay 首次运行与默认单人 · 设计（P1-④.5）

日期：2026-10-08。上游权威源：`2026-10-05-launchbay-design.md`（下称 §x）。
状态：**已落地**（Task 1–5 = 分支 `p45-first-run` 的 `0004f35`…`b94ed88`，三轮评审修复都在里面；权威源改字 = `c26d6f3` + `6923501`；端到端验收与实拍 = `4857071` 起，另成提交。区间记法与验收文档第一节同一口径）。
定位：夹在 ④ 外壳与 ⑤ 交互之间的一片——它改的是**进门与建档的形状**，不是新增子系统。
触发：验收后本人试用时指出「怎么起了带测试数据，很多用户不一定有多人的，默认应该是一人」。

> **2026-10-20 补抬头：本文里「管理员」那一族说法已被后续两次改判掀翻。**
>
> 本文写于 2026-10-08，那时"管理员"是**建档时勾出来的一个属性**（引导建档固定
> `admin: true`，管理页勾「能管理全家」才生效）。今天不是了：
>
> - **2026-10-10**：管理员管账号不管内容，对别人的书签完全不可见也不可改
>   （`2026-10-10-launchbay-admin-boundary-design.md`）。
> - **2026-10-12**：**管理员不再依附于任何档案**——它是一把机器级的 key
>   （`LAUNCHBAY_ADMIN_TOKEN`），与档案无关。于是「档案上有没有 `admin` 字段」这件事
>   没有了：建档请求体里的 `admin` 那一格**不存在了**（送来是 422 且点名该字段），
>   「建成即管理员」与「勾『能管理全家』才生效」两句**整体作废**。
>   **建出来的是第一个人的书签页**，不是管理员。
> - **2026-10-12（另一条）**：**PIN 可以不设**。两张建档表单现在多一格 `nopass`
>   （勾了 = 这一份对局域网里所有人开放）；不勾而 PIN 为空照旧被拒
>   （API 422 点名 `pin`／表单 `?err=badpin`），**两格同给是「没填对」**
>   （`?err=pinboth`／API 422 点名 `nopass`）——从前那份敲进去的 PIN 被静默丢掉、
>   建出一份不设防的档案，而那个人以为门锁上了。
> - **2026-10-11／2026-10-12（语言）**：建档表单多一格 `language`（可选），零档案时
>   引导页上另有一条 `POST /lang` 专门改语言；站级默认语言落在 `data/settings.json`，
>   每一份档案自己的语言落在它自己的 `profile.json`（2026-10-20 起每一份自己一份）。
> - **2026-10-23**：**多一条免凭证的自建档通路**——`POST /api/v1/profiles/new`（机器）与
>   `POST /new`（页面），id 由名字派生（**不接受申报**）、建完**不发会话**。于是建档表单
>   从两张变三张（`/setup`、`/new`、管理页那张）。**"建出来的是第一个人的书签页"那句仍然
>   成立**：第一份档案从来就不带特权（管理员是机器级的那把 key）。名字另有 60 字上限
>   （**写侧**判，超了 422 点名 `title`／表单 `?err=titlelong`）。
>
> **仍然成立的那几条**（别一起掀翻）：形状三档（0 档案 = 建档表单／1 = 一张 PIN 卡片／
> ≥2 = 一排卡片）、**成功不发会话**、建完照样要输 PIN 才能进门、「窗口只开得下一个人」
> （判据在写入时刻重查 `CountProfiles`，与写入同属一次串行化）、以及
> **免凭证建档窗口的判据是磁盘**（不是"谁有资格"）。
>
> 下面正文保留原样，它是"当时为什么这么设计"的记录，**不是现状指示牌**。

## 0. 问题（三条实测事实，不是推测）

以下三处引的都是**改前**那一版的位置（写在这里是记录当时的事实，不是指路标；锚点按字面量给，行号会腐烂）。

1. `internal/httpapi/handlers.go` 的 `handleRoot`：`sess.IsEmpty()` 就直接渲染选择页，**完全不看档案数量**。
   只有一个档案的人每次都要先回答「谁来用？」，而这个选择本来无意义。
2. `internal/render/web/picker.tmpl` 的 `<main>` 里只有 `{{range .Entries}}`，没有 0 档案分支。全新安装打开
   首页是一张**空列表**，页面上没有任何下一步；建第一个档案只能靠 CLI/API 加管理员令牌。
   这台盒子对外宣称「家里人打开就能用」，第一次却需要命令行。
3. 权威源自相矛盾：§15「建档与发 PIN 是一次性人工动作：**管理员在管理页建好**、口头告知 PIN」
   与 §8.8「建档要发 JSON，表单发不出……随 ⑤ 的 JS 落地，这一版按钮不渲染」。本设计按 §15 收敛，
   并给出 §8.8 那条理由为什么不成立的说明（§4 末尾）。

## 1. 拍板记录（人是决定者，实现者不许改口径）

| 问题 | 决定 |
|---|---|
| 只有一个档案时还问不问 PIN | **照旧问**。省掉的只是「谁来用」这一步，档位不动 |
| 0 档案的安装首页给什么 | **浏览器里建第一个档案**（不是「显示一行命令让人复制」） |
| 免令牌建档的窗口什么时候开着 | **只在磁盘上 0 档案时开着**，建成即管理员，之后这条通路自己关闭 |
| 以后加第二个人靠什么 | **本次一并做管理页建档**（管理员会话），不把 ⑤ 的这块留着 |
| 建档表单问哪些字段 | **只问名字和 PIN**，不问 id |
| 管理页能不能造出第二个管理员 | **能**，勾「能管理全家」才生效 |

## 2. 判据与首页三形状

唯一判据是磁盘事实：`Store.CountProfiles()`——`data/profiles/` 下的档案目录数。**不能用
`ListProfiles()`**：它读不动某个 `profile.json` 时会静默跳过（§12 的隔离），于是「装坏了
一个档案」就等于把引导窗口重新打开，第二个人可以合法地再建一个管理员。**不引入任何开关**——没有 `LAUNCHBAY_MULTI_USER`，
没有 `profile.json` 里的模式字段。「多人」= 建了第二个档案；退回单人 = 删到只剩一个。

| 档案数 | `GET /`（无会话）的形状 | h1 | 页面内容 |
|---|---|---|---|
| 0 | 引导页 | 还没有档案 | 一张建档表单：名字 + PIN |
| 1 | 单人进门页 | 那个档案的名字 | 恰好一张 PIN 卡片，不出现「谁来用？」 |
| ≥2 | 选择页（现状） | 谁来用？ | 每人一张 PIN 卡片，逐字不变 |

落点：`render.PickerOptions` 增加 `Heading string` 与 `Setup bool`，**由 httpapi 一次算出**（判据留在
Go 侧那一份，与 `themeAttr`/`validatedAccent` 同一条纪律）；`picker.tmpl` 只按字段印形状，不自己数。
三种页面都保持 `NoStore`：它们都含档案名，缓存住等于把全家名单留给下一个共用这台电脑的人（§7.1）。

## 3. `POST /setup` —— 唯一新增的免令牌写通路

- 判据一条：`CountProfiles() == 0`（目录数，读不出来的坏档案照样占位）。不满足 → **303 回 `/`，不带 `?err=`、不解释**。
  「这台机器已经建过档了」本身就是枚举线索，与 §6.1 里 `/switch` 四种拒说同一句话同一条纪律。
- 字段：`title`（trim 非空）、`pin`（`auth.ValidPinFormat`，4-6 位数字）。没有 id 格子；
  `admin` **不收表单值**——引导建成的档案固定 `admin: true`，它是这台盒子的主人。
- 校验失败：303 回 `/` 带白名单 `?err=`（新增两键 `noname`、`badpin`）。**这里有意不用 422-JSON**：
  `/prefs` 的 422 走 JSON 外壳是因为它的调用方可能是 AI；引导页的读者只会是站在首页的那个人，
  给他一段 JSON 是把他当 AI。
- **成功不发会话 cookie**，303 回 `/`，接着就是第 2 节那张单人进门页，照样要输 PIN。
  这不是保守：提交表单若等于拿到会话，「免令牌建档」就升级成「免令牌进入这台机器」——
  那才是真洞，而它只需要多写一行 `SetSession` 就能出现。
- 落盘走唯一那条 store 通路：`Store.CreateProfile`（存在性检查与串行化在它内部，§4.5）。
- **判据要在写入的瞬间重查，而且与写入同属一个临界区**：`/setup` 走`Store.CreateFirstProfile(in)`——store 级一把互斥锁，锁内先数 `CountProfiles()`，非 0 就返回`ErrBootstrapClosed`，为 0 才在同一个锁里调 `CreateProfile`。按 id 的那把锁管不了这件事：两个不同名字（`dad` 与 `intruder`）各自派生各自的 id，谁也不撞谁，光靠 `ErrExists` 会安静地建出**两个**管理员档案。「只在 0 档案时开着」这句话要在写入时刻也为真，就只能把判据和写入放进同一次串行化里。这不是新加防护，是让本设计的判据真的成立。

## 4. `POST /admin` —— 管理页建档（表单壳，不是第二条 API 面）

同一个 pattern 加一个方法：`/admin` 现在只有 GET，`ServeMux` 允许 GET/POST 并存，语义自然
（管理页的写动作 POST 回管理页）。

- 权限判据一行都不改：现成的 `require(credAdmin, <派生出的 id>)`。**管理员会话本来就能建档**
  （`handleCreateProfile` 在 P1-④ 之前那轮评审就从「只认 Bearer」换成 `require(credAdmin)`，
  当时的理由写的正是「P1-④ 的管理页要用」）。表单通路**不认令牌**，与 `/prefs`、`/switch` 同族：
  `*` 令牌 POST 它得 303，要机器建档走 `POST /api/v1/profiles`。
- 字段：`title` + `pin` + 可选 `admin` 勾选（勾上才建管理员）。
- 判据不许抄第二遍：把 `handleCreateProfile` 现有的「校验 → `HashPIN` → `CreateProfile` → 错误分诊」
  抽成 `createProfile(in) (...)` 一个内部函数，两条壳各自只负责**读外壳**与**写外壳**
  （API 出 JSON，表单出 303 + `?err=`）。这就是 §8.8 那句「硬做就得给每个动作再配一条 form 端点、
  等于把 API 面抄一遍」不再成立的地方：抄的若是判据就违 §5「判据只有一份」；这里共用判据、
  只分外壳，而建档只有两个字段，「表单发不出 JSON」根本不是拦路的理由。
- 失败形状：`noname`、`badpin` 两码 303 回 `/admin?err=`，`admin.tmpl` 顶部补一行 notice
  （这一页今天不接 `?err=`）。
- 设 PIN 与删档**仍在 ⑤**：它们需要二次确认，表单发不出，不在本片范围。

## 5. id 派生（表单不问 id）

`deriveProfileID(title string, exists func(string) bool) string`：

1. `slug(title)`：小写，只留 `[a-z0-9-]`，连续分隔符并为一个 `-`，首尾不为 `-`；
2. 结果过 `model.ValidSlug` 且 `!exists(id)` → 用它；
3. 否则基名 `home`，占用则 `home-2`、`home-3`……**判据是「是否已存在」，不是档案数**——
   删过档的计数会撒谎，而撞名是这件事唯一需要的信号。

不做拼音转写：要么加依赖（违 §2「零第三方」），要么加一张表（违 §11「多出来的件也算失败」）。
纯中文名字的人拿到的是 `home`、`home-2`，而 id 只是 API 与快照目录的 handle；给人看的永远是
`title`，管理页每一行本来就并排印着 `<code>{{.ID}}</code>`。

### 6.1 改判（2026-10-10）：界面文案统一口径

**触发**：本人试用时指出「名称都很乱，不符合习惯」。盘完用户可见文案后，问题不在个别词，
而在**同一个动作有好几个名字**：保存有「存进去／存并继续／存好了。／点保存」四种，
移动到分组有「挪动／挪一条／批量挪动／挪到（N）／把这几条挪到／挪到哪个分组」六种，
打标签有「打标签（N）／给这 N 条打标签／打上／标签／空格或逗号分隔」五种。
再加上语气在「拟人化口吻」与「说明书口吻」之间来回跳（「好了」「存着…」「你自己过期了」
对「点保存」「数据变了」），读起来像三个人写的。

**定的口径**（照中文界面的通行做法，不是重新发明一套）：

1. **按钮用短动词**：保存／创建／移动／打标签／取消，不用「存进去」「打上」这种半截说法。
2. **字段标签用名词**：名称／地址／标题／描述／分组／标签。原「怎么叫」是问句，
   当字段名用不成词。
3. **弹层标题用动宾**：添加书签／移动到分组／批量打标签。
4. **同一个动作只留一个名字**，批量版在后面加「N 条」而不是换一套动词。
5. **去掉拟人化口吻**：状态改成中性事实（「保存中…」「已保存。」「已添加」），
   不让界面替用户做判断（「你自己过期了」指代不清，409 的真事是"你这份页面落后了"）。

**逐条改判与理由**：

| 位置 | 原 | 改 | 理由 |
|---|---|---|---|
| `picker.tmpl` 建档字段 | `怎么叫` | `名称` | 字段标签应是名词；问句不成词 |
| `picker.tmpl` 建档按钮 | `建好，开始用` | `创建并开始使用` | 原句中文不通顺，「建好」是完成时、「开始用」是祈使，硬粘在一起 |
| `picker.tmpl` 坏档主句 | `……读不了，进不去。……才进得去。` | `……读不了，暂时进不去。……才能继续。` | 一句话里「进不去」说了两遍，第二遍还是反过来的说法 |
| `admin.tmpl` 建档字段 | `怎么叫` | `名称` | 同上 |
| `admin.tmpl` 建档按钮 | `新建档案` | `创建档案` | 与「创建」统一，别在两个页面上用两套动词 |
| `app.js` 提交 | `存进去` / `存并继续` | `保存` / `保存并继续` | 短动词 |
| `app.js` 状态 | `好了` / `存着…` / `存好了。` | `已填好` / `保存中…` / `已保存。` | 中性事实，去拟人化 |
| `app.js` 移动 | `挪动`/`挪到（N）`/`把这 N 条挪到`/`批量挪动`/`挪到哪个分组` | `移动`/`移动到（N）`/`把这 N 条移动到`/`批量移动`/`移动到哪个分组` | 「移动」是通行术语；「挪」是口语 |
| `app.js` 打标签 | `打上` | `打上标签` | 「打上」单独看不知道打什么 |

**没动的**：三个被测试逐字钉住的片段——「数据文件读不了」「要在这台机器上修好那个文件」
「进不去的档案：」——以及 h1「还没有档案」「谁来用？」（后者还有一条专门数出现次数的证人）。
本节只动措辞冗余与用词不统一，**不碰任何判据、形状与信息量**。
app.js 的内容指纹随之从 `e6d977e3cacc` 变为 `93063fa1d1bb`，AGENTS.md 与 openapi.json 已同步。
- 预算：引导页与单人进门页都远小于 25 条首屏，仍各跑一次 gzip 读数入既有操作线，**一条线都不抬**。

## 7. 契约同步（一处都不许漏，漏了闸会红）

- `routes()` 新增两项，凭证档位各一，都不新增档位：`{POST /setup, credNone}`（判据是「磁盘为空」而非「谁有资格」，所以它挂在 `credNone` 上而在 handler 与 store 里各查一次同一件事）、`{POST /admin, credAdmin}`（写的是全家名单，判据与 API 那条完全同一个）。不改 `cred` 枚举、不动 `xCredentialNames`。
- `openapi.json`：两个 operation。`/setup` 的 `x-credential: none`，description 里写死「仅当磁盘上
  一个档案都没有；建成的档案固定是管理员；成功后不发会话」——判据写在文档里，不伪装成新的权限类别。
- `AGENTS.md`：表格加两行（含方法列，新方法列闸会自动咬），并在「禁止事项」旁写清
  **AI 建档仍走 `POST /api/v1/profiles`**，这两条是给人按的按钮，不是给 AI 的第二条 API 面。
- 五道既有契约闸 + 本次新增证人全绿才算完成。

## 9. 测试与验收（每条都要能说出「什么改动会让它红」）

1. **三形状**：0 档案页里没有「谁来用？」字样且有 `action="/setup"` 的表单；1 档案 h1 = 档案名且
   恰好一张 PIN 卡片；≥2 与 2026-10-07 的形状逐字一致（用现存夹具当基线）。
2. **`/setup` 建成**：0 档案 → 提交合法名字 + PIN → 磁盘上出现该档案，`profile.json` 的
   `admin == true`、`id` 按 §5 派生、PIN 哈希形状是 `sha256$盐$摘要`（回读磁盘，不看返回值）。
3. **`/setup` 自己关上门**：已有 1 个档案 → POST `/setup` → 303 回 `/` 且 `Location` 无 `err`，
   **磁盘逐字节不变**（判据是磁盘不是状态码；这条同时挡「忘了关窗」和「关了但写盘」两种错）。
4. **成功不发会话**：`/setup` 的 303 响应里 `Set-Cookie` 不含 `lb_profile`。删掉这行保护的写法
   （顺手 `auth.SetSession`）必须当场红。
5. **表单错说人话**：缺名字 → `/` 且 `?err=noname`；PIN 三位 → `?err=badpin`；两个白名单键都在
   `pinNotices` 表里，未登记的键渲染成空（既有纪律）。
6. **`POST /admin`**：管理员会话 → 建成普通档案（`admin:false`）；带 `admin` 勾选 → `admin:true`；
   非管理员会话 303 回 `/` 不写盘；**`*` 令牌 POST 它也 303 不写盘**（表单通路不认令牌）；
   无会话 303 回 `/` 不写盘。
7. **判据只有一份**：同一份非法输入分别打两壳（`POST /api/v1/profiles` 与 `POST /admin`），
   断言**接受/拒绝的判定一致**——文案形状本来就该不同（JSON 点名 reason vs `?err=` 白名单键，
   这是各自外壳的规则，第 3 节写明了理由），所以不能拿「字符串相同」当证人。做法：把校验
   段抽成 `createProfile(in)`，两壳各自不许出现 `ValidPinFormat`/`HashPIN`/`TrimSpace(Title)`
   这三个调用——用一条「本包内这三个符号只出现在一处」的静态证人守（grep 级断言，
   形状类闸在本仓库已有先例）。
8. **窗口只开得下一个人**：0 档案时并发发两次 `/setup`（不同 title，各自能派生出合法 id），
   断言磁盘上**只多出一个**档案，另一个得到不带 `err` 的 303。这条测的是 store 的`CreateFirstProfile`：把它内部的判据从锁内挪到锁外（handler 先查后写），这条必须红——
   否则它就是在测一个不存在的保证。
9. **id 派生表驱动**：`爸爸` → `home`；`Dad` → `dad`；`nas box` → `nas-box`；`---` → `home`；
   `home` 已存在 → `home-2`；`home-2` 已存在 → `home-3`；删掉 `home` 后新建仍是 `home`（证明
   判据不是计数）。
10. **契约面**：五道闸 + AGENTS.md 方法列 + 枚举同集 + openapi 枚举同集全绿；`<script` 计数 0 的
   名单含三张新页面；预算读数不抬线。
11. **实拍**（人在浏览器里，不是断言）：全新空目录起服务 → 建第一个 → 输 PIN 进门 → 顶栏管理 →
    建第二个 → 首页变成「谁来用？」两张卡。这一段是本片真正的验收，前面的都只是必要条件。

## 11. 残余风险（明写，不当 bug 报）

1. **开箱那一刻**：在第一个档案建出来之前，任何能连到这台盒子的设备都能当那个「第一个人」，建成管理员。这是零配置局域网安装的固有前提，不是漏项——写清楚它的边界：
   (a) 判据在 store 的锁内按目录数重查（第 3 节，用 `CountProfiles()` 而不是可读档案数），所以
   **窗口只开得下一个人**，并发提交里只有一个能成，第二个拿到「窗口已关」的 303，不会静默多出第二个管理员；
   (b) 建完之后这条通路按目录数判据关闭（磁盘上有目录就不满足判据）。**"删光所有档案"会把窗口
       重开一次**——那是"这台机器回到没装过"的语义，是主动重置，不是绕过；权威源 §11 那行
       按这个口径写（Task 6 复扫纠正：这里以前写的是"永久关闭、不存在重装绕过"，与 §8.0
       自己那行"0 个 → 引导表单"互相矛盾）。
   (c) 建成不等于进门：引导成功只回 303，不发会话（第 3 节）。
   剩下的就是 (0)：装它的人要在场。这一条不打算用令牌、确认页或限速去解决（§10）。
2. **名字派生 id**：`爸爸` 这种纯中文名拿不到有意义的 id，只能用 `home`/`home-2`。这是「表单不问 id」
   的必然代价，写在这里是为了下一次别再当成缺陷提。
3. **`/setup` 是免令牌写通路**：它写的只有「新建一个档案」这一件事，且只在 0 档案时成立；
   它不许写别的任何东西（加字段之前先回来改这份设计）。
